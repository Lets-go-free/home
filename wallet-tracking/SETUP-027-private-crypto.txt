WalletTracking – Phase 2 / Schritt 1–4
Serverseitige Verschluesselung: isolierter Selbsttest
Stand: 09.09.2026

WICHTIG
=======
Dieses Paket veraendert die produktive Hauptseite und die Discovery NICHT.
Es verschluesselt auch noch KEINE bestehenden Wallets.

Ziel ist nur der belastbare Nachweis:
Supabase Auth -> serverseitiger User-Key -> AES-256-GCM -> Ciphertext in DB
-> serverseitige Entschluesselung.


1. SQL MIGRATION AUSFUEHREN
===========================
Datei:
sql/027-private-crypto-self-test.sql

Im Supabase SQL Editor komplett ausfuehren.
Die Tabelle security_crypto_tests hat RLS bereits in der Migration aktiviert.
Falls Supabase trotzdem eine generische Warnung zeigt, zuerst pruefen, dass im SQL
"alter table public.security_crypto_tests enable row level security" enthalten ist.

Erwartetes Audit am Ende:
- table_name = security_crypto_tests
- rls_enabled = true
- policy_count = 2


2. MASTER-SECRET ERZEUGEN
=========================
Das Secret NICHT von ChatGPT generieren lassen und NICHT ins Projekt/HTML kopieren.

Auf dem Mac im Terminal lokal ausfuehren:

  openssl rand -base64 32

Den ausgegebenen Wert nur in Supabase als Edge-Function-Secret hinterlegen:

  WT_ENCRYPTION_MASTER_KEY_V1 = <dein lokal erzeugter Wert>

Supabase Dashboard:
Edge Functions -> Secrets

Der Wert muss nach Base64-Decodierung exakt 32 Byte ergeben.


3. EDGE FUNCTION DEPLOYEN
=========================
Function-Name:
wallet-private

Datei:
supabase/functions/wallet-private/index.ts

Die Function ist ausschliesslich fuer authentifizierte User ausgelegt.
Kein service/secret key und kein Encryption-Key gehoert ins Frontend.

Deployment wie bei deinen bestehenden Edge Functions.


4. TEST 1 – NUR CRYPTO, OHNE DB
===============================
Nach Login in WalletTracking bzw. mit einer gueltigen Supabase User-Session:

  const { data, error } = await sb.functions.invoke('wallet-private', {
    body: { action: 'self_test' }
  });
  console.log(data, error);

Erwartet:
- ok: true
- algorithm: AES-256-GCM
- kdf: HKDF-SHA-256
- encryption_version: 1
- key_version: 1


5. TEST 2 – DB-ROUNDTRIP, TESTZEILE BEHALTEN
============================================

  const { data, error } = await sb.functions.invoke('wallet-private', {
    body: { action: 'db_self_test', keep: true }
  });
  console.log(data, error);

Erwartet:
- ok: true
- kept: true
- test_id: <UUID>

Danach in Supabase Table Editor die Tabelle security_crypto_tests oeffnen.
In test_ciphertext darf nur ein Wert im Format ungefaehr

  wt1.k1.<nonce>.<ciphertext>

stehen. Der Test-Klartext darf nirgendwo in der DB stehen.


6. TESTZEILE WIEDER LOESCHEN
============================

  const { data, error } = await sb.functions.invoke('wallet-private', {
    body: { action: 'cleanup_tests' }
  });
  console.log(data, error);

Erwartet:
- ok: true


SICHERHEITSEIGENSCHAFTEN DIESES SCHRITTS
========================================
- AES-256-GCM mit zufaelligem 96-Bit Nonce pro Verschluesselung.
- Authenticated Additional Data bindet Ciphertext an User, Record, Feld,
  Encryption-Version und Key-Version.
- Benutzerbezogener Key wird serverseitig mit HKDF-SHA-256 aus dem Master-Secret
  und der authentifizierten User-ID abgeleitet.
- Master-Secret verlaesst die Edge Function nicht.
- Kein frei verwendbarer Encrypt-/Decrypt-Endpunkt.
- Die Test-API verarbeitet nur ihren fest definierten technischen Testwert.
- Bestehende Wallet-Klartextdaten bleiben in diesem Schritt unberuehrt.
