# WalletTracking 8.89 – Historische native Eingangsflows für bestehende Claims

17.11.2026 11:31:08 CET – vorbereitet, noch nicht installiert.

## Ausgangslage

- Die unter 8.88 geprüften **164/164** erfolgreichen DAO1-Claims der festen Wallet `e8b5c835-0db2-4449-bbee-258e28b42bbb` haben je einen kanonischen Claim, positive APTM, positive USD-Werte und eine historische Preisquelle. Ihre Original-APTM-Mengen sind in den bisherigen JS-`Number`-Feldern geringfügig gerundet. **Noch 164 ohne Eingangsflow.**
- Echte On-Chain-Mint-Beträge und historische NFT-Eigentümer wurden read-only neu belegt. Da diese flüchtigen Vorschauen keine persistenten Belege darstellen, MUSS jede Übernahme die Blockchain erneut prüfen.
- Flow-Tabelle: eindeutiger Schlüssel (`user_id,project_key,chain_key,wallet_id,flow_key`), kein eindeutiger `tx_hash`-Constraint, keine benutzerdefinierten INSERT-Trigger. Daher zusätzlicher transaktionsbezogener Duplikatschutz unter Wallet-Sperre.

## Umsetzung

- Neue `SECURITY DEFINER`-RPC `wallettracking_dao_commit_historical_existing_flows_889`, ausschliesslich `service_role`, maximal drei Transaktionen. Installieren führt keine DML aus.
- Fester Wallet-/Projekt-/Chain-Scope, strikte älteste Kandidatenfolge und Anzahl, `FOR UPDATE`-Sperren, historische Ownership-Intervalle und vorhandener eindeutiger kanonischer Claim. SQL vergleicht Original-APTM gegen bestehende Beträge mit höchstens 1e-12 APTM Differenz.
- Bei vollständig erneuter Live-Trace/Mint-Event-/ERC-721-Besitzprüfung im Admin-Edge-Modus `admin-historical-flow-commit-889`: je Transaktion exakt ein Native-APTM-`eingang` mit Original-Rohbetrag und unverändertem bereits kanonischen USD-Betrag; Kandidat `ownership_verified`, `payout_status=verified`, `canonical_existing_verified=true`, `claim_pipeline_status=completed`.
- Explizit **keine** INSERT/UPDATE an `project_nft_claims`, `project_transactions`, Preisankern oder anderen Projekten. Ein Fehler im SQL-Stapel rollt alle drei Flows/Kandidatenänderungen zurück.
- Manuelle Admin-Schaltfläche mit Bestätigungsdialog, bewusst kein unbeaufsichtigter Massenschreibjob; Cron/Live-Worker bleiben AUS.

## Bereitstellung

1. ZIP 8.89 installieren.
2. Migration `20261117112925_dao_historical_existing_claim_flows_889.sql` in Supabase SQL Editor ausführen. Noch kein Flow wird eingefügt.
3. **Edge Function aktualisieren: `supabase/functions/dao-reward-refresh/index.ts`**. Beim Supabase-Deploy müssen zugleich die bereits bestehenden Importe im selben Funktionsverzeichnis vorhanden sein: `payout-coverage.ts`, `price-target-worker.ts`, `asset-policy.js`, `counterparty-policy.js`, `miner-event-853.js`, `miner-batch-preview-856.js`, `miner-multi-event-857.js`, `legacy-native-mint-866.js`, `legacy-flow-proof-886.js`. Nur `index.ts` wurde für 8.89 verändert; sämtliche Module sind im bisherigen Projektstand enthalten.
4. Danach genau **einen** administrativ bestätigten Drei-Flow-Test unter Admin → Audit ausführen, JSON melden und die drei neuen Flows unabhängig per SQL abnehmen, bevor Serienfreigabe erwogen wird.
