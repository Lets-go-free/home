## Konfiguration und Grenzen

`supabase/config.toml` enthält nun `[functions.dao-reward-refresh]` mit `verify_jwt = false`, entsprechend der bereits vorgenommenen Hosted-Einstellung. Cron-Routen prüfen im vorhandenen Code den separaten Secret (mindestens 32 Zeichen, Digest-Vergleich); Admin-Routen nutzen u.a. `authenticateInspectAdmin` mit Benutzer-JWT und `admins.user_id`. Die Gateway-Änderung betrifft alle Routen dieser Funktion. Positive Cron-Authentifizierung live bestätigt; negative Authentifizierung und sämtliche Admin-Routen nach Gateway-Änderung noch live zu prüfen. Keine Secret-Werte in SQL, ZIP oder Logs aufnehmen. `DAO_REWARD_ENABLE_LIVE_WORKER=false` und `DAO_REWARD_ENABLE_MULTI_WALLET_TEST=true` für den Pilot beibehalten.

8.99 bleibt der vorhandene Orchestrator. Pro Aufruf ein geleaster Raw- oder Reward-Schritt, maximal ein kanonischer Claim pro Reward-Schritt. `completed` verlangt u.a. keine verbleibenden geeigneten Claims, keine ungelösten/unbekannten Kandidaten und Referral-Cursor-Abdeckung. `unreviewedWusdt` ist laut Code ein Zähler nicht als Referral verifizierter eingehender wUSDT-Flows bei nicht passenden Transaktionen; kein automatischer Reward, kein eigenständiger Completion-Guard. `completed` und HTTP 200 sind keine unabhängige Vollständigkeitsprüfung. Eigenständiges Referral-Posting fehlt weiterhin.

## Wiederaufnahme (read-only SQL)

```sql
SELECT state, count(*) AS wallets, sum(step_count) AS schritte,
       sum(attempt_count) AS versuche, sum(failure_count) AS fehler,
       count(*) FILTER (WHERE last_error IS NOT NULL) AS offene_fehler
FROM public.wallet_reward_refresh_attempts
WHERE project_key = 'dao1' AND scan_day = DATE '2026-11-24'
GROUP BY state ORDER BY state;
```
