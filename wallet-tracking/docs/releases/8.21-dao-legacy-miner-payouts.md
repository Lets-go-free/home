# WalletTracking 8.21 – Legacy-MineBot-Nachzahlungen erkennen

## Hintergrund
Zwei untersuchte Wallets zeigen 16 bzw. 9 bisher manuell bestätigte wAPTM-Nachzahlungen (8. und 23. Oktober 2026). Genau so viele alte MineBots wurden wenige Tage zuvor zur Migration übertragen. Der ERC-20 `transfer` enthält keine NFT-ID. Keine willkürliche Einzel-NFT-Zuordnung.

## Gemeinsame Erkennungsregeln
- Positiver wAPTM-**Eingang** (Contract `0x110ac02ba3384bc055c13a87766049a74517beda`) vom bekannten Auszahlungssender `0x6d0539de11b95e18cb202a55098e3854b0313022`. Es wird der Contract und Gegenparteiadresse geprüft, nicht der Tokenname.
- Wallet-ID wird aus dem jeweils verarbeiteten User-Job bestimmt; keine fest codierte Liste der zwei Testwallets.
- Manueller DAO-Scan speichert eingehende Token-Flows und nötigenfalls eine ERC-20-Transaktionsidentität (bestehender Code).
- Server-Staging-Scan ergänzt für relevante eingehende Flows eine **insert-only** ERC-20-Transaktionsidentität. Der Persistenz-Abgleich enthält auch bereits gespeicherte, aber früher nicht als Transaktionen sichtbare Flows; paginiert statt nur erster 1000.
- Jeder Hash wird pro Wallet nur einmal eingebracht. Unveränderte Originaltransaktionen werden nicht überschrieben. Keine neuen kanonischen NFT-Claims, keine Preis- oder Reward-Buchungen.
- Unbestätigte Nachzahlungen erscheinen als Prüfkandidaten. Erst User-Entscheidung `confirmed` führt zur Anzeige/Summe als Bot-Claim. `ignored` bleibt ausgeschlossen.
- Bestätigte Einträge erscheinen als „Miner-Nachzahlung (bestätigt) · Alte MineBots“ und unter „Alter MineBot · NFT nicht zugeordnet“. Keine individuelle NFT-Zuweisung.

## Installation
1. Geänderte Dateien unter `wallet-tracking/` ins Projekt übernehmen und Seite neu laden.
2. Die Edge Function `dao-reward-refresh` aus `wallet-tracking/supabase/functions/dao-reward-refresh/` neu deployen, **bevor** serverseitige Job-Erkennung getestet wird. Kein SQL erforderlich.
3. DAO1: Manuell `Daten aktualisieren` für ein neu hinzugefügtes Wallet mit historischer Nachzahlung; neue Prüfkandidaten im Bot-Claims-Tab und Dashboard prüfen. Bereits bestätigte Zahlungen bleiben genau einmal gezählt.
4. Für den bestehenden **manuellen Staging-Testpfad** des Servers einen Job für ein berechtigtes Testwallet ausführen, danach dieselben offenen Prüfkandidaten im UI kontrollieren. Ohne Deployment gilt weiter das alte Verhalten.
5. Test mit Wallet ohne entsprechende Sender-/Tokenkombination: keine Miner-Nachzahlung. Test mit `ignored`: kein Claim.

Kein automatisches Bestätigen, kein Verändern der 25 geprüften Entscheidungen, keine historische NFT-Zuordnung, kein automatischer DAO-Reward-Cron und keine globale Freigabe des unfertigen DAO-Reward-Live-Workers. Die reale End-to-End-Abnahme steht noch aus.
