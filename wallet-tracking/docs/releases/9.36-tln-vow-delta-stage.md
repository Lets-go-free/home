# WalletTracking Phase 9.36 – Serverbasierte Delta-Transferbelege

Build 20261120-101543, Europe/Zurich.

## Einrichtung (in dieser Reihenfolge)

1. Update-ZIP im Projekt installieren.
2. Supabase SQL Editor: `supabase/migrations/20261120101500_tln_vow_reward_delta_stage_936.sql` einmal ausführen.
3. Supabase Edge Function `tln-vow-reward-refresh` mit der **vollständigen** neuen `index.ts` deployen.
4. Mit dem bereits vorhandenen `x-tln-reward-secret` einmal `{"mode":"delta-transfer-stage","maxBlocks":100}` testen. Kein Cron einschalten.

## Funktionsweise

- Wählt ein bereits bekanntes TLN/VOW-Wallet aus einem gespeicherten Discovery-Snapshot und seinem ERC20-Raw-Cache; keine Aufzählung entschlüsselter Wallets. Das Snapshot-Label allein beweist keine vollständige Scan-Abdeckung.
- Startet bei `last_scanned_block − 128` als **unverifiziertem historischen Anker**, führt von dort die nachgewiesene Staging-Folge ohne Lücken fort.
- Liest den BSC-Head, aktive Staking-/Projekt-Tokenregister plus feste Tokens und verwendet dieselbe Alchemy `alchemy_getAssetTransfers`-Schnittstelle wie die Browser-Discovery.
- Speichert nur vollständig paginierte Transfer-Evidenz (maximal 250 erfasste Events je Lauf) in `tln_vow_reward_delta_stage`. `uniqueId`, Tx-Hash, Block, Token, Richtung und Raw-Value bleiben für eine spätere Beleg-/Reward-Klassifikation erhalten.
- Identische Chunks sind durch einen zusammengesetzten Primärschlüssel gegen doppelte Inserts geschützt. Ungültige/fehlende Paginierung und Registernachweise lassen keinen Schreibvorgang zu.
- Ein Staging-Chunk enthält **keine** auf Rewards geprüfte Vollständigkeit und zählt **nicht** als geprüfter historischer Cursor.

## Grenzen

Die Staging-Funktion sammelt Transferbelege. Sie berechnet **noch keine neuen Staking-/Referral-Rewards** und schreibt keine Claim-Zuordnungen. Für den endgültigen Job fehlen weiterhin der vollständige Receipt-/Contract-Call-/State-Delta-/Lifecycle-/Referral-Abgleich und ein transaktionssicherer Import in die kanonischen Reward-Zeilen. Der Cron bleibt deaktiviert. Auch historische Daten **vor** dem alten Cache-Anker sind unabhängig nicht als vollständig belegt.

Die Erstellung einer kompletten täglichen Automatik kann deshalb nicht mit dem Vorliegen dieser Staging-Tabelle gleichgesetzt werden.
