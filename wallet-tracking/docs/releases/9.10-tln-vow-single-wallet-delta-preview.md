# Version 9.10 – TLN/VOW Einzelwallet-Delta-Fenster (Read-only)

## Befund
Die sieben vollständigen BSC-Snapshots stammen aus `tln_vow_staking_scan_cache`, Cache-Typ `verified-discovery-results`. Eine achte Cache-Wallet besitzt ausschliesslich `loan-openings-lifecycle` und daher keinen verifizierten Reward-Snapshot. Die zehn `project_scan_state`-Wallets beziehen sich auf `lp_history_v7_legacy_discovery`, nicht auf den Reward-Scanner. Die bekannte Walletmenge ist **kein** Nachweis der vollständig berechtigten Wallet-Auswahl.

## Änderung
Die bereits geschützte Edge Function `tln-vow-reward-refresh` unterstützt zusätzlich zum bisherigen Request `{}` den Body `{ "mode": "delta-preview" }`. Der neue Modus:

1. lädt wie der bestehende Preflight verifizierte BSC-Discovery-Snapshots und wählt **eine** der ältesten vollständigen Wallets;
2. verlangt `completedStep >= 5`, einen plausiblen Quellblock/Zeitstempel und explizite `process.done.rewards` und `.referral`-Nachweise;
3. liest über `ALCHEMY_API_KEY` einmal `eth_blockNumber` (BSC) und plant ein Fenster `lastCheckedBlock - 128` bis Chain-Head;
4. meldet, ob dieses Fenster das vorläufige Budget von 100'000 Blöcken überschreitet; bei fehlenden Belegen, ungültigen Daten oder RPC-Fehlern stoppt die Vorschau ohne Nebenwirkungen.

Der Output enthält keine Wallet-Adresse, User-ID oder Secrets. Der bestehende Preflight-Modus bleibt unverändert. Die Edge Function verwendet denselben Header `x-tln-reward-secret` / Secret `TLN_REWARD_CRON_SECRET`.

**KEIN fertiger Reward-Worker:** Es gibt weder `eth_getLogs` noch Contract-spezifische Staking-/Rewards-/Referral-/Bonus-Verarbeitung, weder einen persistierten Cursor noch Idempotenz/Queue/Lease. Es werden keine Rewards, Caches oder Datenbankzeilen geschrieben. Das Delta-Fenster ist nur eine technische Vorbereitung und beweist weder Vollständigkeit noch Reward-Gleichheit. Keinen Cron aktivieren.

## Installation / Kontrolle (nur ein Schritt je Freigabe)
1. Edge Function `supabase/functions/tln-vow-reward-refresh/index.ts` erneut deployen. Keine SQL-Migration, kein Frontend-Deployment nötig.
2. Danach mit POST, Header `x-tln-reward-secret` und `{ "mode":"delta-preview" }` einmal lesend testen; nur die Antwort ohne Secret weitergeben.
3. Erst nach Auswertung des tatsächlichen Ergebnisses die serverseitige Portierung der Browser-Schritte als getrennte, nicht schreibende Proof-Engine beginnen. In weiterer Folge eine kontrollierte Vergleichs- und Commit-Phase entwickeln; Cron zuletzt.
