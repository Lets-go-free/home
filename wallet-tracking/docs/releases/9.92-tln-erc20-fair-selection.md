# WalletTracking 9.92 – Faire Auswahl vorhandener und fehlender ERC-20-Caches

**Version:** 9.92 · **Build:** 20261124-103221 · 24.11.2026 10:32:21 CET.

## Problem und Korrektur

9.91 priorisierte in `encrypted-wallet-scan-guarded-stage-preview` stets bereits vorhandene Rohdaten-Caches, unabhängig von ihrem letzten Bearbeitungszeitpunkt. Bei grossen historischen Rückständen konnten Wallets ohne Cache auf unbestimmte Zeit unberücksichtigt bleiben. Die bisherige Read-only-Wallet-Auswahl und Scannerlogik bleiben unverändert; lediglich die Reihenfolge der Kandidaten im bestehenden geschützten Rohdatenmodus ändert sich.

1. Relevante Wallets ohne Rohdaten-Cache zuerst ab Block 0 bearbeiten (in stabiler Reihenfolge).
2. Anschliessend bei gültigen bestehenden Caches den am längsten nicht aktualisierten Cache (`updated_at` aufsteigend) auswählen, statt stets den kleinsten Cursor.
3. Nur gültige Caches mit `complete_from_block=0`, Scanner-Version `erc20-raw-v1` und plausiblen Grenzen fortsetzen; bei Fortsetzung inklusive 24 Blöcken Überlappung.
4. Vollständige Pagination, alle ERC-20-Transfers, Format, Merge, CAS-Update, Ein-Chunk-Begrenzung und ausdrückliche Schreibfreigabe aus 9.91 bleiben bestehen.

## Sicherheit und Tests

Es gibt keine neue SQL-Funktion, Tabelle, Queue, zusätzliche Edge Function oder Cron-Änderung. Der Modus bleibt standardmässig **Read-only**. Nur der bereits vorhandene ausdrückliche Request `commit:true` und `confirm:"single-raw-cache-chunk"` kann genau einen Cacheabschnitt schreiben. Keine Rewards oder Claims werden gebucht. Die Rotation ist eine Auswahlregel, noch kein automatischer Scheduler. Das bestehende kooperative `updated_at`-CAS bietet keinen Schutz gegen ungeschützte alte Browser-Tabs oder direkte Datenbankänderungen.

Test `tln-vow-guarded-stage-fair-selection-992.test.mjs`: fehlende Caches zuerst, älteste vorhandene Caches danach, Rotation nach Fortschritt, 24-Block-Überlappung, aktuelle Caches nicht erneut scannen, ungültige Zeitstempel ausschliessen, Schreibfreigabe erhalten. Bestehende 9.91-Regression ebenfalls ausführen.

## Nächster Schritt

ZIP in GitHub übernehmen, die bestehende Edge Function `tln-vow-reward-refresh` deployen. Danach **nur einen** Read-only-Test mit `encrypted-wallet-scan-guarded-stage-preview`, `commit:false`; erst bei geprüftem Ergebnis einen getrennt bestätigten Schreibtest. Tägliche Reward-Buchungsjobs bleiben deaktiviert. Historische Reward-Vollständigkeit ist nicht nachgewiesen.
