# WalletTracking 8.97 – SQLSTATE 42702 im DAO-Reward-Kandidatenabruf

## Live-Befund 18.11.2026

- 8.96 durch Supabase SQL live abgenommen: Reto 542 Kandidaten, `unresolved=0`, 16/16 `failed_transaction` erfüllen den neuen Guard.
- Tagesqueue 18.11.: 15/15 Wallets `staged`, `unresolved=0`. Import manuell: ein Einzeltest und zwei begrenzte Batches (10+4), 0 Fehler, 0 kanonische Claim- oder Reward-Writes. Ein neuer Reto-Rohscan-Checkpoint wurde erfolgreich erhöht.
- Read-only `cron-staged-preview`: 15 `staged`, Test enabled, Live-Worker aus.
- Erster manueller `cron-staged-one` stoppte **vor** dem Reward-Abschluss: PostgreSQL `42702 column reference "c.user_id" is ambiguous`.
- Unabhängige Queue-Abfrage: Wallet `e8b5c835-0db2-4449-bbee-258e28b42bbb` hat `state=failed`, `attempt_count=2`, `step_count=2`, `failure_count=1`, gespeicherter 42702-Fehler. Die übrigen 14 Wallets blieben staged.

## Ursache / Fix

`wallettracking_dao_next_native_claim_candidate` aus Migration 8.42 deklarierte `c` als PL/pgSQL-Record und verwendete `c` gleichzeitig als Tabellenalias im ersten `UPDATE`. PostgreSQL kann im WHERE `c.user_id` nicht eindeutig zuordnen.

8.97 ersetzt nur diese service-only Funktion; der Record heisst neu `v_candidate`, während der Tabellenalias `c` unverändert bleibt. Inhaltliche Kandidaten-, Transaktions-, Claim-/Flow- und Sicherheitsbedingungen werden nicht verändert. Bestehende 8.42-Klassifizierungen bleiben erhalten. Kein Edge-Deployment erforderlich, keine DML bei Installation.

## Nächster Schritt / Wiederanlauf

1. 8.97-ZIP in GitHub übernehmen und genau die neue SQL-Migration ausführen.
2. Read-only `pg_get_functiondef(...)` prüfen, dass kein `DECLARE c ...%ROWTYPE` mehr besteht; Datenbank-/Queue-Status unverändert.
3. **Achtung:** `cron-staged-one` reserviert nur `staged` oder abgelaufene `reward_running`-Rows. Die betroffene `failed`-Row wird **nicht** automatisch erneut versucht. Nach separater Freigabe einen strikt auf Wallet/Datum/Status/Fehler begrenzten, versioniert dokumentierten Retry vorbereiten; Failure-Counter nicht unbesehen zurücksetzen.
4. Ein manueller Reward-Test auf genau einer Wallet, danach Queue-/Claim-Abnahme. Kein autonomer Massenlauf vor diesem Nachweis.

DAO-Cron und Live-Worker bleiben AUS. Keine Preis- oder Referral-Nachbuchung.
