# WalletTracking 7.93 · 20261107-184337

## Zweck
Die bereits gespeicherten und historisch bewerteten nativen APTM-Miner-Claims sollen
nicht ein zweites Mal als neue Rewards angelegt werden. Es wird ausschliesslich
in der separaten `dao_reward_claim_candidates`-Prüfliste markiert.
Die vorhandenen NFT-/Ownership-/Payout-Prüfstatus bleiben erhalten.

## Sicherheit
- Keine Änderung an `project_transactions`, `project_transaction_asset_flows`,
  `project_nft_claims`, Preisen, Wallet-Snapshots, Scan-Cursorn oder Job-Queues.
- Nur Kandidaten mit beliebigem bisherigen Prüfstatus, passendem Selector und Miner-Vertrag,
  erfolgreicher Transaktion, positivem APTM-/USD-Wert und identischem nativen Claim-Flow.
- Keine Bot-ID erfinden. Historische NFT-Zuordnung bleibt offen.
- Wiederholung: 0 Änderungen, wenn alle passenden Kandidaten bereits klassifiziert sind.
- Manuelles Admin-JWT erforderlich, separater Test-Flag; Live-Worker muss deaktiviert sein.

## Installation
1. ZIP installieren und Webdateien veröffentlichen.
2. Migration `20261107184158_dao_existing_canonical_claims_793.sql` in Supabase ausführen (DDL, keine SELECT-Resultsets).
3. Edge Function `dao-reward-refresh` neu deployen. Cron deaktiviert lassen.
4. `DAO_REWARD_ENABLE_TEST_IMPORT=true`, `DAO_REWARD_ENABLE_LIVE_WORKER=false`.
5. Manueller POST mit gültigem Admin-JWT: `{"mode":"classify-existing-test-wallet"}`.
6. Vorher/nachher `{"mode":"inspect-test-wallet"}` abfragen. Die neue Antwort
   enthält `canonicalAlreadyPricedClaims`.

Die Klassifikation erfasst nur die fest hinterlegte Test-Wallet. Die 100 Kandidaten
sind nicht pauschal als korrekt eingestuft: Die Funktion prüft jede Transaktion.
Die genaue Anzahl kann daher zwischen 0 und 100 liegen.
