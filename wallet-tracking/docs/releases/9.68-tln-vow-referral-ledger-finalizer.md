# Phase 9.68 – Kontrollierte Referral-Mint-Zuordnung

Build 20261122-214644 · 22.11.2026 21:46:44 CET.

Für zuvor eindeutig belegte Referral-Mints gibt es jetzt einen eigenen kanonischen Beleg-Ledger. Die bereits entwickelte manuelle Step-5-Strong-Regel und der in 9.63–9.67 erfasste SmartNode-/Receipt-Nachweis werden **nochmals** geprüft: fremder Staker, erfolgreiche Receipt, exakter Token und Mint-Logs, positiver Wallet-Nettozufluss, vollständiger bis zur Empfängerwallet verifizierter SmartNode-Pfad mit Level 1–20. Bereits in gespeicherten manuellen Discovery-Strong-Zeilen vorhandene Tx-/Token-Paare werden nicht übernommen.

Die Eindeutigkeit ist `(user_id,wallet_id,chain_key,tx_hash,token_address)`. Mengen bleiben exakte Raw-Integerstrings. Nur Service-Role schreibt; angemeldete User dürfen dank Owner-RLS ausschliesslich eigene Ledger-Zeilen lesen. Die existierende Dashboard- und Discovery-Anzeige wird **noch nicht** um die Ledger-Zeilen erweitert, um Doppelzählung zu vermeiden.

## Installation

1. ZIP installieren.
2. SQL `supabase/migrations/20261122214509_tln_vow_verified_referral_ledger_968.sql` einmal ausführen.
3. Edge Function `tln-vow-reward-refresh` neu deployen.
4. Mit der **bereits funktionierenden Vault-Authentifizierung** den POST-Body `{"mode":"referral-claim-finalize"}` senden. Das ist read-only (`dryRun:true`). Erwartet `receiptInventoryComplete:true`, `inspectedReceipts`, `eligibleReferralClaims`, `skippedExistingSnapshotClaims`, `skippedIncomplete`.

**Nicht `commit:true` ausführen, bevor eine reale positiv belegte Live-Kandidatenzeile und ihre fachliche Zuordnung geprüft wurden.** Der Tages-Cron bleibt inaktiv. 0 Kandidaten sind bei aktuell nicht vorhandenen neuen Referral-Mints erwartbar, aber kein vollständiger Abnahmetest.

Regressionsprüfung: `tests/tln-vow-referral-claim-finalizer-968.test.mjs` deckt strenge Positivevidenz, idempotenten Insert, fehlende Parent-Chain, falschen Betrag und bereits in Discovery vorhandene Claims ab. Keine RPC-Aufrufe im Finalizer.
